# author

Authoring: what does this network become after these edits? A change — retime a trip, add a stop, extend a calendar, fork the plan into the next pick — is a list of typed edits applied atomically to a registered NETWORK document. The answer is the next document under its content hash (registered: chain the next change on it), with its validation issues and warnings — the authoring loop in one op. The last document is never touched (the host wholesale-replaces its copy); removals refuse while anything references the entity. The edit vocabulary lives in transit-network. Assemble for anyone who changes a network: a planner's UI, a script, an agent.

## apply

Apply `edits` in order, atomically, to the registered document: set_plan (fork / stamp a pick — {plan:{id,name,effective_from}, through?}: with through, the period's last day, the fork carries the calendar — every WEEKLY service type still running in the calendar's final week (its last range ends within six days of the latest date any type names) whose last range ends before it now ends on it, a closed period stays closed; dated-only types gain nothing, next year's holidays are the planner's to add; the calendar is read up to through; then the fork's calendar is its period, D-138: every range is cut to effective_from..through, open at the end without through, and a range or exception outside it goes — every service type stays, even one left with no date; a through before effective_from is refused), set_name, retime_trip {trip, to_secs} (move a one-start trip: it keeps its id, its running times, and its blocks — they name it by id), add_trip {pattern_trips, start_secs, id?} (a new trip timed by its pattern's profile covering the start; id minted {pattern_trips}@{start} when omitted, reported in `created`), remove_trip {trip} (gone everywhere: its pattern trips, emptied, go; its block closes up and goes when emptied), upsert_* / remove_* for stop, route, pattern, service_type, pattern_trips, block (upserts replace the whole entity under its id: read it from the document, change it, send it back), and the GESTURES — one edit per thing a planner does, each carrying its coherence rule: add_stop / add_route / add_pattern / add_service_type {from} / add_pattern_trips / add_block (id minted when omitted — first free s1, r1, pat1, cal1, svc1, b1 — and reported in `created`); add_pattern_through {route, direction?, stops, run_secs, name?, id?} (a new pattern laid through `stops` in order — a new route's, or another variant: each visit at the great-circle length of the legs before it, estimated, never published; the first and last visits timepoints; one all-day profile running run_secs end to end; in direction, one of the route's; named name, else "<route> → <last stop>"; drawn stop to stop; refused for fewer than two stops, an unknown stop, a stop twice in a row, an unknown route or direction, or a zero run time — then set_headway with its pattern gives it trips); update_stop / update_route / update_pattern / update_service_type / set_pattern_trips_refs (field-wise, references checked); set_direction {route, id, name} (add or rename one of a route's directions) / remove_direction (refused while a pattern runs in it), update_pattern {direction} (one of its route's directions, "" for none; a route move leaves it in none unless the same edit places it); draw_alignment {pattern, points:[{lat,lon}…], redraw: one|all, id?} (redraw a pattern's line, naming what moves: one gives the pattern a new alignment of its own — id, else minted al{n}, reported in `created` — and the other patterns on its old line keep it; all redraws the alignment it runs, so every pattern on it moves; the redrawn patterns are reported in `touched`, and their stop distances keep their meters but stop claiming to be published); insert_pattern_stop {index?} (before visit index, default the last stop, halfway along that leg, non-timepoint, unscheduled on every trip), remove_pattern_stop / toggle_timepoint (middle visits only; every timing profile and every trip's times stay aligned — a new timepoint takes its neighbours' midpoint in each profile, and each trip is scheduled there where it ran), set_pattern_stop, add_timing_profile / remove_timing_profile (one always stays) / set_timing_profile / set_timepoint_time; toggle_service_day {day: mon..sun}, add_service_range {start?, end?} (a date left out continues the last range: start where it ends, end at start; a key with no range needs a start; never ending before it starts) / set_service_range / remove_service_range, set_service_exception (one per date, date order) / remove_service_exception; set_band / add_band / remove_band {trip} (a frequency trip's bands; one always stays); add_block_trip {block, trip:{trip}} (in order of first start; a layover stays only while its two trips stay adjacent) / remove_block_trip / set_layover {after_trip, secs | null} (only between two trips). The TIMETABLE gestures address a route + direction (+ service type) — the directory's `timetable` — and apply across every pattern of the direction: set_headway {route, direction, service_type, from_secs, to_secs, headway_secs, pattern?} (frequency by period: a trip every headway from from_secs until before to_secs; one-start trips already in the window move to the nearest slots in order, keeping their ids, times, and blocks; open slots are new trips with fresh ids on the pattern the trip before runs, timed by its profile, unassigned; surplus trips go everywhere; frequency trips are left alone), set_span {route, direction, service_type, first_secs?, last_secs?, headway_secs?} (trim past a bound; extend to it at headway_secs, else the edge's median gap, on the edge trip's pattern), adjust_running_time {route, direction, service_type, from_secs, to_secs, delta_secs} (the direction's one-start trips under that service type departing in the window run delta_secs longer, negative shorter, in proportion along each trip — each keeps its id and start; other service types, frequency trips, and the profiles are untouched), insert_direction_stop {route, direction, stop, after} / remove_direction_stop {route, direction, stop} (by stop id on every pattern of the direction; endpoints stay). direction null or omitted means the route's patterns in no direction; pattern trips a gesture empties are removed and new ones minted ({service_type}:{pattern}) are reported in `created`; only one-start trips are moved. An out-of-range index or a missing reference is a named error, never a silent no-op. One edit that cannot apply (an unknown id; a removal of something still referenced — a stop a pattern visits, pattern trips a block carries) rejects the whole change as an error naming the edit's position. The answer: the next network_hash (already registered), the document itself, its issues (gate export — a block's wait is layover_infeasible {gap_secs, required_secs, required_by} when it is under the recovery required there: with work_rules_hash, the work rules' most specific rule (policy, it wins); else the smallest authored layover at that terminal (terminal) for a pair carrying an authored layover — a layover's own authored length is slack, never the requirement, D-9) and warnings (never gate: unassigned trips, a pick with no service in its period), `created` ({kind, id} per entity the change made), and `touched` ({kind, id} per entity it altered beyond that: the patterns a draw_alignment redrew — nothing moves silently).
