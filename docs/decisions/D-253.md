# D-253 — What shape does a coded refusal take in a module's answer?

Topic: Versioning and deployment.
State: Decided.
Answer: 2026-11-25. Every error is an object with a `message`. A
refusal that a host acts on also carries `code` and its fields. Nothing
is in production, so every host changes in one change. The user: "as
you said, there is not production deploy to protect, lets go with the
cleaner path"
Context: every module error is one string, `{"error": "<message>"}`
(`cap_abi::outcome`). Four places in the hosts recover by matching that
text (`docs/units/refusal-codes.md`). A refusal that a host acts on
gets a stable code and its fields. The code is a Rust type, so its
schema reaches the manifest and the HTTP contract (D-249).
Options:
- Additive (recommended). `error` stays the message string. A coded
  refusal also carries `"refusal": {"code": "<code>", ...fields}`. A
  host that reads only `error` keeps working, and the HTTP contract
  gains a field, an expansion the lock accepts. Cost: two fields where
  one could do. Both are written from one Rust value, so they cannot
  disagree.
- `error` becomes an object, `{"message", "code", ...fields}`, for
  every error. Cost: every host and every worked example changes in one
  step, and the contract contracts, so the lock needs a release that
  expands first.
Pinned by: none yet.
Blocks: nothing. The work is `docs/units/refusal-codes.md`.
