# D-233 — When does the receive path refuse a write whose reference is broken?

Topic: The planner's UIs.
State: Encoded provisionally. The existence check is built on both
sides of the read: a person's write is judged in its log's receive op
as of the seqs its writer read (`read_seq`, `read_seqs`) and refused
for a reference added to a missing record, and warned as of now. Also
built: cap-log `references` and `naming`, `store verify`'s and `store
revert`'s reports, and the unjudged record of a newer version. A log
with no entries is not judged. The first rule is built: a stop
request's stop, judged in the stops log's receive op on the write's
date (D-238). The other kinds' rules, and the client's module for a
rule a page runs, are planned (`docs/units/reference-rules.md`,
item 6).
Context:
- A write carries the seq it read for each log it depends on. This is
  a list, not one number. D-189's outbox carries the seq it read.
  Whether it covers each log is to be checked.
- The server runs the kind's domain check twice. Each referenced
  document is folded at the seq of the check.
  - As of the read seq, with the module that the client names in
    `produced_by` (the server keeps every build it served). A failure
    is refused. An honest client ran the same check on the same data,
    and would not send the write. A module that the server never
    served is refused.
  - As of now, with the server's module. A failure is accepted with a
    warning. The world changed after the writer read it.
- A writer with no read seq read now.
- The server accepts a client module only from the builds it served,
  within a window that the operator sets. A rogue client then cannot
  name an old module to get older, looser rules.
- A check that cannot judge never refuses. After a rollback, a target
  can be in a version that this build reads ahead (D-186), with a
  state the rule does not know. The check answers a warning that names
  the newer version. Otherwise a rollback blocks the writes of every
  kind that names the target.
- A rule changes in one release. The as-of-read check runs under the
  client's module, so a tighter rule warns about an older client's
  write and never refuses it. A rollback does not turn an honest write
  into a refusal.
- A revert or a retire answers the references that name what it
  removes. `store revert` lists the declared references into the
  commits it drops, beside the commits.
- `store verify` reports each broken loose reference, with the entry
  that broke it. A finding names the kind table's hash, the module's
  hash, and the seq, so it can be judged again after any release or
  rollback.
- A domain check refuses only a contradiction within what the writer
  saw. It never refuses on plausibility. Each refusal rule states why
  the write is impossible, beside its law.
- The owning module holds a rule for each reference: a referrer in
  state X needs a target in states Y. An existence check is the rule
  where Y is every state.
- A law: a write that the client's check passes as of seq s passes
  the server's check as of s.
Options:
- Refuse as of the read seq, warn as of now (encoded here).
- Never refuse across documents. Every client is treated as stale, so
  a rogue client can write.
- Refuse as of now, as SQL does. An honest offline write that raced a
  removal is lost.
