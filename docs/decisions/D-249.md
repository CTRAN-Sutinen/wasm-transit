# D-249 — Where do the HTTP contract's wrapper shapes come from when it is generated?

Topic: Versioning and deployment.
State: Decided.
Answer: 2026-11-25. Rust answer types, through `schemars`, with the
answers that Go composes hand-written in the overlay. The user: "rust
types with the go overlay, per your suggestion."
Context: the queued work "The HTTP contract, generated"
(`docs/units/README.md`) generates
`server/openapi.json`. The routes come from the mux, the whole-document
bodies from the kind table and the locked schemas, and the prose from a
hand-written overlay. Left are the answers around a document: `from`,
the document hashes, `refusals`, `issues`, `landed`, `seq`, and the
references. Most come out of a capability's op, which answers them in
Rust, and the server passes them on as opaque JSON ("The Go server
stays scaffolding"; `docs/architecture/server.md`, "No domain logic in
Go"). A few the server composes in Go itself: `/readyz`, `/manifest`,
the answers while the bucket does not answer, and the pointer answers.
Today only `transit-log`'s receive inputs (`Write`, `OpCall`) derive
`schemars::JsonSchema`. The answer types do not.
Options:
- Rust answer types, through `schemars` (recommended). Each op's
  answer type derives `JsonSchema`. gen-manifest writes the schemas
  beside the kind schemas, and the generator reads them. The answers Go
  composes stay in the overlay as hand-written schemas. Cost: a derive
  on each answer type, and the Go-composed answers still written by
  hand, in one place.
- Go structs, with a schema reflector. The server declares a Go type
  for each answer it sends, the passed-on ones too. Cost: a Go mirror of
  each Rust answer type, which goes against the server holding answers
  as opaque JSON, and a second place for each shape. The contract tests
  catch a drift between them.
- The overlay holds every wrapper shape by hand. Only the routes and the
  whole-document bodies are generated. Cost: each wrapper shape is
  still written twice, but the routes and the documents are not.
