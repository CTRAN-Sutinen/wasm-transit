# The registry and the runner

The registry has two roles: the modules agents and people run
(this section), and the published schema of every document kind
("Document schemas", below).

The registry (`registry/`, published by every `just caps`; `just
registry` runs the gates first): immutable blobs + one evidence
record per capability (contracts, agent context, which gates ran —
none for a plain `just caps` — at which commit, the digest of
the source tree that built it, and the cargo profile: `release`, or
`wasm-fast` from `just caps-fast`, the iteration loop's build, which a
gated publish refuses) + a pointer. `caps-run` recomputes
the source digest on every run and says on stderr when the registry
was published from another tree (`just test` gates the agreement).
It is the
artifact agents and humans pull SANDBOXED COMPUTE from —
`tools/caps-run.mjs` verifies blob bytes against the pinned hash and
runs ops behind a worker-termination wall-clock guard (`--timeout`).
A session runs its steps in command-line order and may span
capabilities (`--cap` switches; each module verified and
instantiated once): documents cross between modules BY REFERENCE
(`"network":"$net.network"`), the way a host hands the same bytes to
each module, and `--as` names results so references survive
reordering. A session holds each result as the module's JSON text
and parses one only when a reference reaches into it — a parsed
real-size answer is millions of objects every later collection
re-marks. Sessions do not persist — a later session re-imports.
Registry records and the browser manifest are BOTH generated by
`cargo run -p cap-abi --features gen-manifest --bin gen-manifest` —
one source of contracts, two surfaces. A capability's agent context
(its purpose and each op's description) is the `OPS.md` beside its
crate, Markdown an agent edits like any doc; the generator reads it
and refuses one whose op sections are not the capability's ops. The
worked examples are computed in the generator, never written. `just test` gates the runner
itself (the fixture feed hash is stable, so registry/fixture drift
fails the gate).

## Document schemas

Every `just caps` also publishes each document kind's JSON Schema and
a worked example: gen-manifest generates the schema from the kind's
serde type (`schemars`) and computes the example, and writes
`registry/schemas/<kind>.v<N>.schema.json`,
`registry/examples/<kind>.v<N>.json`, and the index
`registry/documents.json` — per kind its bus `kind`, its `store_kind`
(the store envelope's kind, when the store persists it), its
`schema_version`, the files' paths and hashes, and the registry's
evidence. A reader maps a blob's envelope (`kind`, `schema_version`)
to its schema there (`docs/FORMATS.md`); `server/reader_test.go`
checks every example against its schema and reads a store with
nothing but the bucket, the schemas, and FORMATS.md.

The schemas are generated, not kept: `registry/` is gitignored and
rewritten by every `just caps`, so it holds the version each kind
writes today and no other, nothing gates a serde change that moves
one, and no deployment serves them. Keeping every version, the gate,
and serving them are `docs/units/document-versioning.md`, item 5.
